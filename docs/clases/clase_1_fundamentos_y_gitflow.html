Bloque 1 · Por qué versionar

Cuatro preguntas que esa carpeta no puede responder

¿Qué cambió entre _FINAL y _FINAL_correg? Hay que abrir los dos y comparar a ojo.

¿Quién lo cambió y por qué? El nombre del archivo no lo dice. La persona que sabía se fue del proyecto.

¿Cómo vuelvo a como estaba el martes? Si nadie hizo copia el martes, no se puede.

¿Cómo trabajamos dos a la vez? No se puede. Uno espera, o después alguien pega los cambios a mano.

Git responde las cuatro. No porque sea mágico, sino porque guarda el historial en lugar de guardar copias.

Bloque 1 · Por qué versionar

El cambio de mentalidad

Con carpetas

Guardás estados completos. Cada copia es un archivo entero, y lo que pasó entre una y otra se perdió.

El historial vive en el nombre del archivo y en la memoria de quien estuvo.

Con Git

Guardás la secuencia de cambios. Cada paso queda registrado con quién, cuándo y por qué.

Cualquier estado anterior se reconstruye. El historial es parte del proyecto, no de la memoria de nadie.

La consecuencia práctica: dejás de tener miedo a romper algo. Todo lo que está commiteado se puede recuperar.

Bloque 2 · Conceptos

Siete palabras y ya está

Repositorio

La carpeta del proyecto más su historial completo. Cuando clonás, te traés las dos cosas.

Commit

Una foto del proyecto en un momento, con autor, fecha y un mensaje que explica el porqué. Es la unidad de trabajo.

Branch (rama)

Una línea de trabajo paralela. Te permite hacer cambios sin afectar lo que los demás están usando.

Merge

Traer los cambios de una rama a otra. La mayoría de las veces Git lo resuelve solo.

Conflicto

Cuando dos ramas cambiaron la misma línea. Git no adivina: te pide que decidas vos.

Remoto

La copia del repositorio que vive en el servidor — GitHub, GitLab, Azure DevOps. Es el punto de encuentro del equipo.

Pull Request

Pedir que tus cambios entren a otra rama, para que alguien los revise antes. No es de Git: lo agrega la plataforma.

Bloque 2 · Conceptos

El ciclo, entero

# 1. Traer la última versión
git pull

# 2. Abrir una rama para lo tuyo
git checkout -b feature/mi-metrica

# 3. Trabajar, y guardar el avance
git add metricas/ventas/mi_metrica.sql
git commit -m "feat: agregar métrica de clientes activos"

# 4. Subirlo al servidor
git push -u origin feature/mi-metrica

# 5. Abrir el Pull Request, que alguien revise, mergear

Ese es el 90% del uso diario. No hace falta memorizarlo: se pega en un papel y en dos semanas sale solo.

Bloque 2 · Conceptos

La única distinción que sí conviene entender

git add

Elegís qué entra

De todo lo que tocaste, marcás lo que va a formar parte del próximo commit.

git commit

Lo registrás en tu historial

Queda guardado en tu máquina. Nadie más lo ve todavía.

git push

Lo publicás

Recién ahí llega al servidor y el resto del equipo puede verlo.

El malentendido más frecuente: "ya lo commiteé" no significa que tu compañero lo tenga. Hasta que no hacés push, el cambio existe sólo en tu computadora.

Bloque 3 · GitFlow

Ramas sí, ¿pero cuáles?

Git te deja crear ramas. No te dice cuántas, ni cómo llamarlas, ni cuándo mergearlas. Eso lo tiene que decidir el equipo.

GitFlow es una de esas decisiones ya tomada. Un convenio: cinco tipos de rama, cada uno con un propósito, un origen y un destino.

No es la única forma de trabajar ni la mejor para todo proyecto. Es la más difundida, y la que mejor se explica.

Bloque 3 · GitFlow

Las dos que viven para siempre

main

Lo que está publicado

Cada punto de esta rama salió alguna vez a producción. Es la referencia de qué está funcionando hoy.

Nadie commitea acá directo. Sólo llegan merges de release y de hotfix, cada uno con su etiqueta de versión.

develop

Lo que va a salir

Todo lo terminado que todavía no se publicó. Es la sala de espera de la próxima versión.

Nadie commitea acá directo. Sólo llegan merges de feature.

Que nadie commitee directo no es burocracia: es lo que garantiza que todo cambio pasó por una revisión.

Bloque 3 · GitFlow

Las tres temporales

feature/*

Nace de develop → vuelve a develop

Una por cada cosa nueva. Existe para que lo que estás haciendo a medias no le rompa el día a nadie. Se borra después de mergear.

release/*

Nace de develop → va a main y también vuelve a develop

La ventana de estabilización. Cuando decidís qué entra en la versión, cortás acá y a partir de ese momento sólo se corrigen errores. Mientras tanto develop sigue recibiendo trabajo nuevo sin bloquear la salida.

hotfix/*

Nace de main → va a main y también vuelve a develop

La única que no nace de develop. Cuando producción se rompe, develop está lleno de cosas a medio terminar que no pueden salir. El hotfix nace de lo publicado, corrige sólo eso, y sale.

Bloque 3 · GitFlow

El error más común, y el más silencioso

Hacer el hotfix y mergearlo sólo a main

Producción queda arreglada. Todo el mundo contento.

Tres semanas después sale la versión siguiente — que viene de develop, que nunca se enteró de la corrección — y el bug vuelve.

Nadie lo detecta en el momento porque no falla nada. Se descubre cuando el mismo error reaparece y ya nadie se acuerda de por qué.

Regla mnemotécnica: si la rama toca main, tiene que tocar develop también.

Ejercicio 2 y 3 · 30 minutos

Recorrer el historial y abrir un PR

git log --oneline --graph --all | head -30

Ese dibujo es GitFlow, ya aplicado: cuatro features que entraron, dos versiones publicadas (v1.0.0 y v1.1.0) y un hotfix que salió a corregir producción.

Contá los merges: los de release son cuatro y los de hotfix dos. Cada uno aparece dos veces porque fue a main y también a develop. La regla del slide anterior, dibujada.

Después abrís tu Pull Request hacia develop — y revisás el de otro participante. Al menos un comentario.

Hay un PR real esperando revisión en el repositorio: el de la tasa de conversión.

Cierre de la clase 1

Hasta acá

  1. Git guarda cambios, no copias. Por eso puede responder qué, quién, cuándo y por qué.
  2. El ciclo diario es siempre el mismo: pull, rama, add, commit, push, Pull Request.
  3. Las ramas existen para no pisarse. GitFlow sólo pone nombres y reglas a algo que ya necesitabas.
  4. Si toca main, toca develop. Release y hotfix siempre son dos merges.
